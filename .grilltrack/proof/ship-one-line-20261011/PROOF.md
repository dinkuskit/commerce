# Ship gets what people typed as one line

Decision: `commerce-ship-sync-001`, reopened and re-locked on Ronald's "Swap them" (01:30:45 UTC 2026-10-11, decision card in the project thread "Buildout status and next steps", "Swap hidden line breaks for spaces in orders Commerce sends Ship?"). Built on main `c7e8e64` (commerce#100 merged); Node 22.23.2.

- Why: dinkuskit/ship PR 23 at head 4660579 answers 422 to any order text holding a character in `[\u0000-\u001f\u007f-\u009f\u2028\u2029]` (`NOT_ONE_LINE` in `service/src/order.ts`), and Commerce then holds that order version back until it changes. Commerce's own checks refuse only `[\u0000-\u001f\u007f]`: the checkout delivery address and the owner's address fix (`src/features/checkout-contact/index.ts`), catalog names, which become order line names (`src/features/catalog/normalize.ts`), and a hand-typed carrier or tracking number (`note` in `src/features/orders/store.ts`). The shopper's email is ASCII only and order and item ids are generated, so no other field could carry them.
- `bin/verify-commerce full` on 4c1eda3: passed. Typecheck and repo audits clean; unit 530 pass, integration 56 pass, sandbox browser 10 pass, native local-stock 1 pass, Orders browser 1 pass.
- Registry bundle: 128,424 bytes on main, 128,647 with this (+223), leaving 2,425 under 131,072; backend sha256 `4d00fb13965ed463d7977560dda9679cbedbe5dc132c23bbaf84ab9cef666866`.
- Unit (`tests/features/orders/ship.test.mjs`): an order whose address holds U+2028, U+2029 and NEL (one field nothing but NEL) and whose item name holds U+2028 and NEL reaches Ship as `"Fixture Shopper"`, `"1 Example Way Unit 2"` and `"Wool Hat Blue"`, with the empty field left out; the owner's address fix and a hand-typed carrier and tracking number go the same way (a carrier with nothing left is left out); every string Ship receives passes Ship's own rule; and the order keeps every field as typed. The store name follows the same rule, so `" \t Fixture\u0007 Hat\nShop \u2029 Co\u0085\u007f  "` becomes `"Fixture Hat Shop Co"`. Both tests fail on main's code.
- Ship's side: Commerce's sync from this branch (4c1eda3) and from main (c7e8e64), each bundled with esbuild, ran inside PR 23's own Workers test harness at head 4660579 against its real Worker and Durable Object (a scratch check committed in neither repository). The same pasted order got 422 from main's code, and Ship kept nothing; it got 200 from this branch's code, Ship kept the one-line text, and later the Completed version with carrier `"US PS"` and tracking `"9400 SYNTHETIC"`. Ship's own 11 tests passed in the same run.

Not covered: Ship's hosted service is not merged or deployed. Checkout, the catalog and Complete order accept what they accepted before; only what Commerce sends Ship changes.
