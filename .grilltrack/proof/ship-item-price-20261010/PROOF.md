# Ship gets the price paid for each item

Decision: `commerce-ship-sync-001`, reopened and re-locked on Ronald's "yes no no" (23:10:45 UTC 2026-10-10, project thread "Where Ship stands"), answering three questions about what Commerce sends Ship: the price paid for each item, yes; the order total and the shipping the shopper paid, no; the shopper's phone number, no. The re-locked choice also names the store key trade (`commerce-store-key-001`, merged in commerce#98) as where the `ship:orders` pass comes from. Built on main `28cec7b` (commerce#98 merged) in 0296273; Node 22.23.2.

- `bin/verify-commerce full` on 0296273: passed. Typecheck and repo audits clean; unit 526 pass, integration 56 pass, sandbox browser 10 pass, native local-stock 1 pass, Orders browser 1 pass.
- Registry bundle: 127,926 bytes on main, 127,945 with item prices (+19), leaving 3,127 under 131,072; backend sha256 `b98f7f9dc8419cbf4fd8393271e2e884b34c6db573c58a2b2986c413a559c84b`.
- Unit (`tests/features/orders/ship.test.mjs`): each line Ship gets carries `unitPrice` exactly as the kept paid order has it: two hats at `{ currency: "USD", minor: "1250" }`, a scarf at `"899"`, and an item since removed from the catalog at `"100"`, sent without a weight. Digital items stay out, and nothing sent to Ship contains a total, a payment id, a receipt or a phone number, though the fixture's order has all of them.
- Installed workerd runtime (`tests/integration/registry-checkout-services.test.mjs`): after a real checkout, the order Ship receives on its traded `ship:orders` pass has `lines: [{ catalogItemId: "hat", name: "Hat", quantity: 2, unitPrice: { currency: "USD", minor: "250" }, weightOz: 4.5 }]`.
- `unitPrice` is the paid order's own line price for one of the item, before any order-level coupon; Registry stores take no coupons in v1 (`registry-coupons-unhooked-v1`). `docs/contracts/commerce-handoffs.md` and `docs/implementation/registry-ship-sync.md` list it, and the handoff notes for Ship were updated the same evening.

- Ship's side, run together with Commerce (a scratch check committed in neither repository): Commerce's compiled `syncShip` from this branch, bundled with esbuild, ran inside dinkuskit/ship PR 23's own Workers test harness against its real Worker and Durable Object (heads 82b3cb3 and 680ccd8), with passes shaped like DinkusKit.com's (ES256, issuer `https://dinkuskit.com/account`, audience `dinkus-ship`, scope `ship:orders`). Ship kept each line's `unitPrice` and `weightOz` exactly as sent, left out the digital item, and kept nothing holding the total, payment id, receipt or phone. A Canadian address got 422 and Commerce waited until the address was corrected to a US one, then Ship kept version 2. A label recorded in Ship completed the order in Commerce with USPS and its tracking number, Commerce acknowledged it, and Ship kept the Completed version; a stale label and one for an order Commerce never had were acknowledged and changed nothing. On 680ccd8, Commerce's largest possible order (100 lines with 160-character Japanese names to an address with 200-character fields, 67,491 bytes) is kept too.

Not covered: Ship's hosted service is not merged or deployed yet, so no real order has reached it.
