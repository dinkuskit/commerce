# Orders sends orders to Ship (commerce-ship-sync-001, commerce-allowed-hosts-ship-dinkuskit-com)

Measured from f31fd79 (commerce#96) plus 8086caf (agent order access, `commerce-orders-api-001`, still proposed), Node 22.23.2.

- `bin/verify-commerce full`: passed. Typecheck and repo audits clean; unit 526 pass, integration 51 pass, sandbox browser 10 pass, native local-stock 1 pass, Orders browser 1 pass.
- Registry bundle: `backend_bytes=129752 headroom_bytes=1320` (127,780 with agent order access; sending orders to Ship adds 1,972).
- What is sent and when (`tests/features/orders/ship.test.mjs`): each order with a delivery address goes to Ship once per version as `dinkuskit.commerce.ship-order/v1`, with the order number, version, status, test flag (false only for live orders), the delivery address, the shopper's email and the lines that go in the box with each product's weight in ounces when set; digital items are left out, an item since removed goes without a weight, and no prices, totals, payment ids or phone numbers are sent. Recording the version Ship took does not raise the order's version. An address fix, Complete order and Move back to Processing each send the new version.
- Labels (same file): a label for an order still Processing at the labeled version completes it with Ship's carrier and tracking number and the order then goes to Ship as Completed; a label for an older version, a Completed order, an unusable tracking number, an unknown order or a malformed order id changes nothing; every label is acknowledged, and one seen again after a lost acknowledgement changes nothing.
- Failures (same file): Ship down when listing, acknowledging or receiving changes nothing and the next sync carries on; 422 records the version as never labelable until the order's next change; a missing pass calls nothing; malformed label lists and more than 100 labels change nothing; at most 10 orders go per sync and a backlog drains over later syncs.
- Orders page (`tests/features/orders/status.test.mjs`): the page syncs when it opens and after each saved change, not for reads, refused or outdated changes; Ship being down never breaks the page or a change.
- Setting (`tests/features/checkout/registry-provider-admission.test.mjs`): `ship`, like `coupons`, is admitted only as exactly an https origin and a nonempty audience; anything else, extra keys or an origin with a path is refused; both services and `mode` can be set together.
- Manifest (`tests/features/checkout/installed-context.test.mjs`, `tests/integration/registry-checkout-services.test.mjs`): `network:request` allows exactly payments.dinkuskit.com, coupons.dinkuskit.com and ship.dinkuskit.com.
- Installed workerd runtime (`tests/integration/registry-checkout-services.test.mjs`, last two tests): the compiled Registry backend sends a paid physical order to a Ship stand-in that verifies the store's `ship:orders` pass, only when Orders opens (Checkout never calls Ship), and keeps working with Ship after the Payments pass has expired; the background check (`commerce-checkout-wakes` cron) completes the order from a bought label with USPS and the tracking number, acknowledges it and sends the Completed version; the Orders page shows the tracking number; an agent's list calls nothing and an agent's Move back reaches Ship right away; a label list over 128 KB is refused by the same bounded reader as Payments' answers, with nothing acknowledged or completed. Without `ship`, without a Ship pass, or with the Payments pass in its place, nothing calls Ship and Orders keeps working.
- The two workerd tests first lived in their own file and timed out starting workerd beside the other workerd file in a full run; they now run in the same file, one runtime at a time, and two further full integration runs passed 51 of 51.

Not covered: Ship's hosted service does not exist yet (handoff `/mnt/project-files/ship-handoff/ship-push-handoff.md` in the project), DinkusKit.com issues no `ship:orders` pass yet, and nothing switches on the background check or renews a store's passes on a real install.
