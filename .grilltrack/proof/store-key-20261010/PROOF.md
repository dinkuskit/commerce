- Installed workerd runtime (`tests/integration/registry-checkout-services.test.mjs`), with a stand-in for DinkusKit.com's trade at the real host `https://dinkuskit.com` and issuer `https://dinkuskit.com/account` (the test answers EmDash's DNS check for that one name in-process, so no request leaves the test):
  - Each trade is `POST https://dinkuskit.com/api/store-passes` with `Authorization: Bearer <store key>`, `Content-Type: application/json`, no cookie, and exactly `{ site_id, scope, audience }`. Preparing a checkout trades nothing; starting one trades once for `payments:checkout` and uses that pass for both Payments calls; a status check trades once; opening Orders trades once for `ship:orders`; the background check trades at most once for each. Across all of that, the key appears in exactly the five trades and in no request to Payments or Ship.
  - The key goes only to DinkusKit.com whatever issuer the settings name: with the issuer set to the Payments, Coupons or Ship host (each an allowed host), checkout, Orders and the background check send every request to `https://dinkuskit.com/api/store-passes` and nothing anywhere else; the passes it hands back name DinkusKit.com, not that issuer, so start answers `recoverable-failure` and Payments and Ship get zero calls.
  - Twelve refusals each cost one trade and reach Payments zero times, and start answers `recoverable-failure`: 401 `invalid_store_key`, 403 `site_mismatch`, `service_not_enabled`, `service_cut_off` and `store_suspended`, 429 `rate_limited`, 503 `signing_unavailable`, a redirect, a 200 without `access_token`, truncated JSON, a coupon-scoped pass and a pass issued in the future. A good answer afterwards checks out.
  - Expired, wrong-scope and wrong-site passes from the trade fail before Payments transport. Replace key stops the old key at once, and pasting the new one, even with a space and a line break around it, checks out again with the bare key as the Bearer token. Without a store key, prepare answers `UNAVAILABLE` and the background check trades and calls nothing.
  - Upgrading from the three pass settings: a store whose `installedCheckoutCredential`, `installedCheckoutCouponsCredential` and `installedShipCredential` still hold valid passes, saved as the version before the store key saved them, and no store key: prepare answers `UNAVAILABLE`, Orders opens, and Orders and the background check send nothing at all. After the owner pastes a store key, checkout and Ship work on traded passes, and none of the three old passes appears in any request.
  - Ship gets each order on its own traded pass with the Payments pass already expired; with Ship turned off, or a Payments pass handed out in its place, nothing calls Ship.
  - Coupons unhooked: the shipped backend contains no `/quotes`, `/redemptions` or `coupons:checkout`. With the coupon service in the settings and a valid, missing, wrong-scope or wrong-site coupon pass, `SAVE10` and `save10` are refused as `COUPON_UNAVAILABLE` (`try-later`) with no cart write, no coupon service call and no Payments call, and the same capability checks out without a coupon, trading only for Payments.
