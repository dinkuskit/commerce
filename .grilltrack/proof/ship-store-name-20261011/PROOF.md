# Ship gets the store's name

Decision: `commerce-ship-sync-001`, reopened and re-locked on Ronald's "Yes yes" (00:11:12 UTC 2026-10-11, project thread "Where Ship stands"), answering that thread's question 2 of 00:08 UTC: Commerce sends the Site title with each order, and Ship uses it as the sender name on the shipped email. His answer to question 3 in the same message puts the shopper reply-to email on Ship's own Settings page, so nothing else changes in Commerce. Built on main `34ce103` (commerce#99 merged); Node 22.23.2.

- `bin/verify-commerce full` on 8776200: passed. Typecheck and repo audits clean; unit 529 pass, integration 56 pass, sandbox browser 10 pass, native local-stock 1 pass, Orders browser 1 pass.
- Registry bundle: 128,286 bytes on main, 128,424 with the store name (+138), leaving 2,648 under 131,072; backend sha256 `6251bedc1c134ae83f6bbbeb8aef3ecd96f5fdd7678ee83fbfb77aa234e091cc`.
- Where the name comes from: EmDash 1.2.0 gives every plugin `ctx.site` (`SiteInfo`, documented as always available). Its `name` is the host's configured site name or else the `emdash:site_title` option, and `createSiteInfo` makes it `""` when neither is set. The workerd sandbox runner writes the same site info into each sandboxed plugin's wrapper. `resolveRegistryShip` passes `ctx.site?.name` on the Ship connection; nothing else reads it.
- Unit (`tests/features/orders/ship.test.mjs`): every order in a sync carries the same `storeName`. Control characters (tab, BEL, line feed, NEL, DEL) are removed and the ends trimmed. 250 `é` become 200, and a cut at 200 never ends on half an emoji or on a space. No Site title, an empty one, spaces only or control characters only send no `storeName` key at all. The earlier tests, whose connection has no name, still see exactly the old record.
- Installed workerd runtime (`tests/integration/registry-checkout-services.test.mjs`): after a real checkout, the order Ship receives carries `storeName: "Synthetic fixture"`, the Site title the runtime fixture gives EmDash's sandbox runner.
- Ship's side: dinkuskit/ship PR 23 (head 680ccd8) keeps only the fields it reads and drops any others (`parseShipOrder`), so orders carrying `storeName` are taken before Ship reads it. Commerce's compiled `syncShip` from this branch (8776200), bundled with esbuild and given the Site title `" Fixture\u0007 Hat Shop\n "`, ran inside PR 23's own Workers test harness against its real Worker and Durable Object (a scratch check committed in neither repository): every order it sent carried `storeName: "Fixture Hat Shop"`, Ship answered each with 200 except the Canadian address it refuses with 422 as before, and Ship's kept orders hold only the fields it reads. Ship's own 11 tests passed in the same run. Ship's text rule (not blank, at most 200 by JavaScript `.length`, no C0 control character or DEL) is what Commerce's cleaning guarantees, so the field cannot turn an order into a 422 once Ship reads it. The handoff note for Ship lists the field and asks Ship to drop a bad one rather than refuse the order.

Not covered: Ship's hosted service is not merged or deployed and does not read `storeName` yet, so no shipped email has used it.
