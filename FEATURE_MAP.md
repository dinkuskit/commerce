## Boundary rules

- A feature may import its own files, declared shared modules, third-party packages, and another feature only through that feature's `index.ts`.
- Files outside a feature may reach it only through its `index.ts`; `src/index.ts` is the package composition root.
- Tests consume publishable behavior through the package build or the feature's public entry, not a private implementation file.
- Commerce owns catalog identity, sellability policy, price, and the configured inventory-provider binding. It does not own stock quantities, locations, reservations, movements, or a fallback stock ledger.
- `dinkus.inventory-provider` contains no network client, credential, quantity, or provider fallback. Its binding retains only provider, pool, and default fulfillment-location identities. Its append-only EmDash claim adapter owns operation selection, not stock truth. Registration emits only pool, canonical SKU, and a one-time display-name default; an active Commerce link persists only the permanent Inventory SKU identity.
- `dinkus.inventory-setup` owns the permanent Commerce site identity and the singleton stored binding. It accepts only a catalog item ID from the browser and resolves the provider through an injected port. It contains no provider transport, credentials, service discovery, stock quantity, or pool migration.
- Storefront display settings, managed-product backorder policies, manual unmanaged availability, catalog prices, product media references, and the placeholder image use records isolated from the Inventory binding and catalog item, so those bounded setting writes cannot clobber concurrent location or managed-SKU state changes.
- Product media are references into EmDash's Media Library by media id only (`catalog_media` / `catalogMedia`, `storefront_placeholder_image` / `storefrontPlaceholderImage`). Commerce stores no file, URL, alt text or size, declares only `media:read`, reads alt and dimensions live, and leaves public URLs, `srcset` and sizes to the storefront host through the exported preset helpers over EmDash's image endpoint.
- `dinkus.storefront-availability` reads only the configured default fulfillment location for managed products. It stores no quantity, never uses a pool aggregate or fallback provider, and returns unavailable when managed setup or authoritative stock truth cannot be proven. Unmanaged products read only their Commerce manual status and never contact Inventory or expose quantity. Missing Regular is not listable; `$0` Regular is a free listable product.
- The catalog pilot creates only draft simple products and permits only its bounded backorder-policy, unmanaged-availability, and Regular/Sale price updates. The Products admin page lists those products and edits Regular, Sale, and In stock / Out of stock / On backorder when a product is unmanaged. Native Commerce v1 keeps the Manage stock slider after Regular/Sale, gray and disabled by default, with adjacent Coming soon. Only an explicit host-owned `enableLocalStockManagement` constructor option plus trusted loopback request and configured site URLs may enable the slider and mounted admission. When both constructor and runtime site URLs are present, both must be loopback; a local constructor cannot mask a public or malformed runtime site, and a production constructor fails closed even if runtime is local. Missing or blank runtime may use an explicit trusted constructor URL. Missing both, or a blank/malformed present site URL, fails closed. Browser hostname, `NODE_ENV`, URL queries, and request-body overrides cannot. Registry/sandbox Block Kit 1.2.0 cannot render a true disabled slider (`NEEDS_HOST_SUPPORT`); the current Coming-soon notice is an honest fallback, not acceptance of Bobby's requested Registry UI. Mounted create/save refuse tracking changes unless that local-dev triple is true. Existing managed products stay managed, can still edit prices, and remain fail-closed without a provider. Commerce → Settings → Catalog sets whether out-of-stock products show on the shop. General product editing, deletion, MCP, checkout, publication, package publication, deployment, and production mutation remain outside this slice.

## Registry-safe admin proof driver

- Build: `npm run build`; authoring manifest `emdash-plugin.jsonc`, entry `src/plugin.ts`.
- Runtime UI: Block Kit JSON on the private `admin` route; no `adminEntry`, no plugin React.
- Reach: Commerce Products (`/products`); Commerce Settings (`/settings`), Catalog section.
- Action: add Name + SKU, save Regular/Sale/manual status, observe Manage stock Coming soon as unavailable, save Hide out-of-stock products.
- Observe: SQLite persistence after reload, refused prices retained, unmanaged availability without Inventory, omitted tracking fields preserve existing managed state, malicious enable refused, anonymous writes denied.
- Registry disabled slider: `NEEDS_HOST_SUPPORT`. Installed `@emdash-cms/blocks` 1.2.0 `ToggleElement` has no `disabled` field and `ToggleElementComponent` never forwards `disabled` to Kumo Switch. Commerce does not emit an unsupported live toggle.
- Registry media picker: `NEEDS_HOST_SUPPORT`. Installed `@emdash-cms/blocks` 1.2.0 `renderElement` returns null for `media_picker` on plugin admin pages, so Commerce renders its own Media Library chooser (`ctx.media.list`, image/*, Use/Next/Cancel) and previews through the host's media item URL.
- Proof: `npm run test:sandbox` with a real workerd runner on a new EmDash 1.2.0 SQLite DB; screenshots in `.tmp/sandbox-proof/<run>/`. Opted-in native local-stock browser: `npm run test:sandbox:native-local-stock` (`playwright.native-local-stock.config.mjs`); the full verifier invokes it after the standard sandbox suite.
- Kernel-only public entries under `features/{catalog,inventory-setup,storefront-availability}/kernel/index.ts` exclude native route/runtime imports. The existing feature public entries still export native routes for compatibility.
- Fresh sandbox storage uses snake_case collection names. Populated native camelCase storage migration is not included; never substitute this artifact on an existing native store.
- Public Registry listing/installation remains unproved until separately authorized publication. Local sandbox operation is not Registry discovery proof.

## Applied checkout composition limits

Qualified composition is applied: checkout feature ownership, public
`./features/checkout` export, and checkout unit/integration globs are present
while native `./admin`, `./sandbox`, `./descriptor`, sandbox build, and native
lock/dependencies remain. Native `createPlugin` and the Registry/sandbox
descriptor now register `checkoutCarts` / `checkout_carts` plus public
`checkout/guest/prepare`, `checkout/guest/start`, and
`checkout/guest/status`. Default production
Payments binding stays absent (`PAYMENTS_UNAVAILABLE`). Real Stripe traffic,
Inventory whole-basket adapters, shopper H1 UI, contact/delivery, and shipping
remain separate obligations. `package.json#dinkuskit.pendingComposition`
records the mounted-public-routes / Stripe-unrun limit.

## Applied fixed-bundle composition limits

Qualified composition is applied: fixed-bundles feature ownership, public
`./features/fixed-bundles` export, and fixed-bundles unit glob are present
while native `./admin`, `./sandbox`, `./descriptor`, sandbox build, native
lock/dependencies, and existing checkout/catalog contracts remain.
Fixed-bundles stays unmounted. Native `createPlugin` does not register bundle
routes, storage, or admin. Shared-file overlaps are `src/index.ts` (export
only), `package.json` (feature export + unit glob only), and this feature row.
Authoritative set-price, order snapshot adoption, runtime mount, and
managed-provider reservation remain separate obligations. This module alone
does not prove sale, fulfillment, or provider success.

## Installed Orders inspection

Authenticated admins with `plugins:manage` open Commerce Orders (`/orders`) in the installed sandbox admin. Inspect opens the exact canonical order ID; Back to orders returns to the paginated list. The page scans `checkout_carts` paid attempts, shows recorded receipt/attempt/provider IDs, original item prices and available pricing breakdown, distinguishes provider-paid from zero-payable, and always reports fulfillment as Not recorded. Empty storage and unavailable/ambiguous records are distinct. No payment or fulfillment mutations are exposed.

Driver: `tests/integration/orders-inspection.test.mjs` exercises the real EmDash SQLite repository, canonical checkout writes, storage/UI pagination, duplicate and malformed records, and read-only inspection. `tests/sandbox/orders-blocks.spec.mjs`, via `npm run test:sandbox:orders`, exercises the installed Registry-format artifact, list/detail/back, keyboard, mobile, empty and unavailable states with synthetic completed orders. `tests/orders-blocks.test.mjs` owns forged-caller authorization denial. Run `bin/verify-commerce full`. Local installed proof is not Registry publication or live Stripe acceptance.

## Merchant settings (`dinkus.store-settings`)

entry: `./features/store-settings`. Native Store embeds the same form through a

## Command-line client boundary

The `dinkus-commerce` CLI ([docs/CLI-SPEC.md](docs/CLI-SPEC.md)) owns
`cli/`, `bin/dinkus-commerce.mjs`, and `tests/cli/`. It is not a feature and is
not part of the package build: it reaches Commerce only over the mounted
EmDash plugin HTTP routes, imports nothing from `src/` or `dist/`, and nothing
in `src/` imports it, so it adds no bytes to `dist/sandbox/plugin.mjs`.
`tests/cli/dinkus-commerce.test.mjs` enforces that boundary and checks the
CLI's route ids against the package's exported route constants.
