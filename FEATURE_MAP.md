## Boundary rules

- A feature may import its own files, declared shared modules, third-party packages, and another feature only through that feature's `index.ts`.
- Files outside a feature may reach it only through its `index.ts`; `src/index.ts` is the package composition root.
- Tests consume publishable behavior through the package build or the feature's public entry, not a private implementation file.
- Commerce owns catalog identity, sellability policy, price, and the configured inventory-provider binding. It does not own stock quantities, locations, reservations, movements, or a fallback stock ledger.
- `dinkus.inventory-provider` contains no network client, credential, quantity, or provider fallback. Its binding retains only provider, pool, and default fulfillment-location identities. Its append-only EmDash claim adapter owns operation selection, not stock truth. Registration emits only pool, canonical SKU, and a one-time display-name default; an active Commerce link persists only the permanent Inventory SKU identity.
- `dinkus.inventory-setup` owns the permanent Commerce site identity and the singleton stored binding. It accepts only a catalog item ID from the browser and resolves the provider through an injected port. It contains no provider transport, credentials, service discovery, stock quantity, or pool migration.
- Storefront display settings, managed-product backorder policies, manual unmanaged availability, and catalog prices use records isolated from the Inventory binding and catalog item, so those bounded setting writes cannot clobber concurrent location or managed-SKU state changes.
- `dinkus.storefront-availability` reads only the configured default fulfillment location for managed products. It stores no quantity, never uses a pool aggregate or fallback provider, and returns unavailable when managed setup or authoritative stock truth cannot be proven. Unmanaged products read only their Commerce manual status and never contact Inventory or expose quantity. Missing Regular is not listable; `$0` Regular is a free listable product.
- The catalog pilot creates only draft simple products and permits only its bounded backorder-policy, unmanaged-availability, and Regular/Sale price updates. The Products admin page lists those products and edits Regular, Sale, and In stock / Out of stock / On backorder when Manage Stock is off. Commerce → Settings → Catalog sets whether out-of-stock products show on the shop. General product editing, deletion, MCP, checkout, publication, package publication, deployment, and production mutation remain outside this slice.

## Registry-safe admin proof driver

- Build: `npm run build`; authoring manifest `emdash-plugin.jsonc`, entry `src/plugin.ts`.
- Runtime UI: Block Kit JSON on the private `admin` route; no `adminEntry`, no plugin React.
- Reach: Commerce Products (`/products`); Commerce Settings (`/settings`), Catalog section.
- Action: add Name + SKU, save Regular/Sale/manual status, toggle Manage stock, save Hide out-of-stock products.
- Observe: SQLite persistence after reload, refused prices retained, dormant status restored, unmanaged availability without Inventory, anonymous writes denied.
- Proof: `npm run test:sandbox` with a real workerd runner on a new EmDash 0.41.0 SQLite DB; screenshots in `.tmp/sandbox-proof/<run>/`.
- Kernel-only public entries under `features/{catalog,inventory-setup,storefront-availability}/kernel/index.ts` exclude native route/runtime imports. The existing feature public entries still export native routes for compatibility.
- Fresh sandbox storage uses snake_case collection names. Populated native camelCase storage migration is not included; never substitute this artifact on an existing native store.
- Public Registry listing/installation remains unproved until separately authorized publication. Local sandbox operation is not Registry discovery proof.
