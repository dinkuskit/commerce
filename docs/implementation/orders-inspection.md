# Installed Orders inspection

The sandbox descriptor declares `/orders`. The host authenticates private admin interactions; the controller additionally requires trusted `admin-page` context and `plugins:manage`. Browser-supplied identity is never trusted. Native compatibility pages are unchanged.

Checkout's frozen order stays in `checkout_carts[].attempts[].order`. Since the paid-order handoff (`docs/contracts/commerce-handoffs.md`, GrillTrack `commerce-paid-order-handoff-001`), Checkout also hands each paid order to Orders as a `dinkuskit.commerce.paid-order/v1` record, and Orders keeps its own copy in the `orders` collection under the order id. The Orders page reads only those copies. Checkout hands the record over when it records the payment and again on every later check of that paid checkout; a repeat with the same contents is a no-op and a different one is refused, so the first copy is never replaced. When the page finds no copies, and when an admin presses Bring in missing orders, Orders asks Checkout for its paid orders (`listPaidOrders`) and keeps a copy of each one it lacks, reporting any that differ from a kept copy.

Bringing orders in accepts only paid attempts with matching attempt identity. Duplicate order IDs, invalid aggregates, repeated/missing cursors and scan exhaustion fail closed. Reads of either collection scan at most 100 storage pages of 100 records and present 25 orders per admin page in canonical-ID order. The detail view also shows when Checkout recorded the payment, or Not recorded for orders paid before that was kept. Selection uses the encoded complete order ID, not a position. Missing selection is unavailable, never a fabricated order.

Recorded order/receipt/attempt/provider IDs, item names, catalog IDs, quantities, unit prices and total are displayed. When present, the frozen pricing snapshot supplies subtotal, coupon discount, net items and shipping. No pricing is recomputed from the current catalog. Missing historical breakdown is explicitly not recorded. No shipping state is inferred from payment: every order starts Processing. Ticket ids saved at checkout stay on the order and are not listed on the page. Pack builds the Inventory body (`stock.pack` for one ticket, `stock.pack_all` for every ticket; no order number; the command id is a SHA-256 digest of the command so a retry replays Inventory's stored result) and sends it through a host-wired `InventoryPackPort` (`src/features/orders/pack.ts`, HTTP adapter for Inventory `POST /v1/stock/pack`). Only a 200 answer echoing that command id with `packed`/`packed_all` reports Packed in Inventory; every other answer, an unconnected store, or a transport failure reports Not packed. Orders writes nothing either way, buys no label and does not mark the order delivered. The installed Registry admin has no Inventory pack binding yet, so it reports Not packed.

Owner changes (GrillTrack `commerce-order-identity-001` and `commerce-order-status-001`) are the page's only writes, each bound to the order version the owner opened and raising it by one; a stale version changes nothing. Correct address (Processing orders with an address) keeps Checkout's frozen copy and stores the correction beside it. Complete order records `completed: { at, carrier?, tracking? }` (carrier and tracking optional, at most 64 characters each); the order then shows Completed, its completion details and Move back to Processing, which asks for confirmation and removes the completion. A Completed order's address is locked. Completing sends no email.

Agents and the `dinkus-commerce` CLI reach the same reads and changes through the private `orders` route (`src/features/orders/api.ts`, GrillTrack `commerce-orders-api-001`), one JSON `POST` per action: `list` (optional status and offset, 50 orders a page by order number), `show`, `complete` (optional carrier and tracking) and `reopen`. EmDash requires `plugins:manage` and, for API tokens, the `admin` scope; the handler checks the administrator again. Changes name the order version and use the same owner-change rules as the page, so a stale change is `outdated` and nothing changes. The answer carries each order's number, version, status, test mark, total, lines, option choices, where it ships to (the corrected address when there is one), the shopper's email and phone, and its completion. The route does not bring in missing orders or number older ones; the page still does. Only the Registry build mounts it. The contract for callers is [docs/CLI-SPEC.md](../CLI-SPEC.md#orders-commands).

When the store has Ship's hosted service, the page brings Orders and Ship up to date when it opens and after each saved change, and the route does after each saved change: labels Ship bought complete their orders, and Ship gets each order version it has not taken ([Orders and Ship](registry-ship-sync.md)). A sync that cannot reach Ship never changes what the page shows. A Processing order with an address then also shows Create shipping label, a link to Ship's label page for that order ([Create shipping label](registry-ship-sync.md#create-shipping-label)).

The Orders installer and shared admin helpers plus bounded checkout/coupon factoring retain the localization runtime, payment behavior, validation and unchanged official backend cap. Packaging must be revalidated after every source change; build success alone is insufficient.

Proof uses local SQLite and real workerd with the installed harness site (`tests/installed-coupon-site`, kept under its original name). Canonical completion uses a synthetic payment port and free checkout; no provider payment is mutated. Installed checks cover anonymous and forged-editor list/detail denial, keyboard selection, desktop/mobile, empty/unavailable recovery, and unchanged canonical storage during inspection. See FEATURE_MAP for executable drivers.

The initial delivery verifier reproduced a browser-proof mismatch: metadata now renders in one section, but the proof required each value to occupy a separate text element. Independent AutoReview P3 reported the same issue. Both installed and preview proofs now assert the visible labeled values without depending on that element subdivision; the installed and preview reruns passed. This is a proof repair, not removal of receipt/payment assertions.

When this was written the backend was close to the official 131072-byte per-file limit. Coupons have since left the Registry artifact (`docs/implementation/registry-coupons-deferred.md`), and `npm run build:sandbox` now repeats official package validation on every build.

Local installation uses the fixture’s genuine Registry-source runtime loading path with an unsigned package. Publisher verification, Registry discovery/consent, populated native migration, production deployment and live Stripe acceptance are not established.
